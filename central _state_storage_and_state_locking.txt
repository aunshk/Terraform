# Terraform Remote State with S3 and DynamoDB (State Locking)

This guide explains how to configure **Terraform remote state storage in Amazon S3 with state locking using DynamoDB**.
This setup prevents concurrent state modifications and is the **recommended best practice** for Terraform on AWS.

---

## Prerequisites

Ensure the following are available before starting:

* AWS account
* Terraform installed (`>= 1.3`)
* AWS CLI installed and configured
* IAM user or role with **AdministratorAccess**
  *(or equivalent permissions for S3 and DynamoDB)*

Verify AWS access:

```bash
aws sts get-caller-identity
```

---

## Step 1: Create an S3 Bucket for Terraform State

The S3 bucket stores the Terraform state file.

### 1.1 Create the Bucket

```bash
aws s3api create-bucket \
  --bucket my-terraform-state-bucket \
  --region eu-north-1 \
  --create-bucket-configuration LocationConstraint=eu-north-1
```

### 1.2 Enable Versioning (Recommended)

```bash
aws s3api put-bucket-versioning \
  --bucket my-terraform-state-bucket \
  --versioning-configuration Status=Enabled
```

### 1.3 Enable Encryption

```bash
aws s3api put-bucket-encryption \
  --bucket my-terraform-state-bucket \
  --server-side-encryption-configuration '{
    "Rules": [{
      "ApplyServerSideEncryptionByDefault": {
        "SSEAlgorithm": "AES256"
      }
    }]
  }'
```

---

## Step 2: Create DynamoDB Table for State Locking

Terraform uses DynamoDB to lock the state file during operations.

### Required Configuration

* Table name: `terraform-locks`
* Partition key: `LockID`
* Type: `String`
* Sort key: **None**

### Create Table Using AWS CLI

```bash
aws dynamodb create-table \
  --table-name terraform-locks \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST \
  --region eu-north-1
```

Wait until table status is **ACTIVE**:

```bash
aws dynamodb describe-table \
  --table-name terraform-locks \
  --region eu-north-1
```

---

## Step 3: Ensure IAM Permissions

### If Using AdministratorAccess

If your IAM user or role already has:

```
AdministratorAccess
```

➡️ No additional IAM setup is required.

---

### Recommended (Least Privilege) IAM Policy

Attach the following policy if admin access is not used:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject",
        "s3:DeleteObject",
        "s3:ListBucket"
      ],
      "Resource": [
        "arn:aws:s3:::my-terraform-state-bucket",
        "arn:aws:s3:::my-terraform-state-bucket/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetItem",
        "dynamodb:PutItem",
        "dynamodb:DeleteItem",
        "dynamodb:UpdateItem",
        "dynamodb:DescribeTable"
      ],
      "Resource": "arn:aws:dynamodb:eu-north-1:ACCOUNT_ID:table/terraform-locks"
    }
  ]
}
```

Attach this policy to the IAM user or role running Terraform.

---

## Step 4: Configure Terraform Backend

Create a backend configuration file.

📄 **backend.tf**

```hcl
terraform {
  backend "s3" {
    bucket         = "my-terraform-state-bucket"
    key            = "dev/terraform.tfstate"
    region         = "eu-north-1"
    dynamodb_table = "terraform-locks"
    encrypt        = true
  }
}
```

### Notes

* `key` defines the state file path inside S3
* Use different keys for different environments (dev, qa, prod)

---

## Step 5: Initialize Terraform

Run:

```bash
terraform init
```

If a local state exists, Terraform will prompt:

```
Do you want to migrate your existing state to the new backend?
```

Type:

```
yes
```

---

## Step 6: Verify State Locking

### Test Locking
1. Run `terraform validate` in one terminal
2. Run `terraform plan -out=tfstate` in one terminal
3. Run `terraform apply "tfstate"` in one terminal
4. Start another `terraform apply` in a second terminal

Expected behavior:

```text
Error: Error acquiring the state lock
```

This confirms DynamoDB locking is working correctly.

---

## Step 7: (Optional) Environment-Based State Management

### Option 1: Separate State Files

```hcl
key = "dev/terraform.tfstate"
key = "prod/terraform.tfstate"
```

### Option 2: Terraform Workspaces

```bash
terraform workspace new dev
terraform workspace new prod
```

---

## Best Practices

* Do not commit `.tfstate` files to Git
* Enable S3 versioning for recovery
* Always use DynamoDB locking
* Use IAM roles instead of access keys in CI/CD
* Use least privilege in production

Delete resources


terraform destroy

👉 Delete the S3 bucket LAST

##
DynamoDB (State Lock)

DynamoDB table is only used for locking

It does not store the state file

Once terraform destroy is done, no lock is needed

Safe to delete immediately

S3 Bucket (State File)

S3 bucket contains the Terraform state file

Terraform backend still references it
